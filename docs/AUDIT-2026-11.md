## 0. Executive summary

The web application is broader than the MVP document assumes and thinner in the two places that matter most: **money and seats**.

| | |
|---|---|
| Database migrations | 33, all applied |
| Tables | 41 |
| Edge functions | 10 |
| Web routes | 31 |
| REST route handlers | 3 |
| Server actions | ~40 across 8 modules |

**Four findings block a paid pilot.** Detail and file references in §5:

1. Four payment edge functions take identity and amount from the request body while holding a service-role key. One lets any signed-in caller release another driver's escrow.
2. Seats are never decremented when a booking is made. The function that does it correctly exists and is never called.
3. There is no hold expiry on a booking.
4. Nothing server-side checks that a driver is a driver before they publish a trip.

**One finding is a scope contradiction, not a bug.** Decision 6 reads *"No wallet or escrow in the MVP — Decided"*. A wallet ledger, top-up, withdrawal and escrow release are already built and migrated (§5.5). CEO decision, not an engineering fix.

**The mobile descope moves two items from "covered elsewhere" to "missing".** Push notifications and booking-linked chat were previously acceptable as mobile-only. With web as the only product in this repository, both are now unmet P0 requirements with real build cost (§5.6, §5.7).

**Supabase stays the single shared backend for web and Kotlin**, and §1.1 sets out why that is the cheapest and fastest option available. The one piece of work it implies: about 12 write actions currently live in Next.js server actions, which only the web can call. Moving them into Supabase is the same work the P0 defects already require.

## 1. Website and backend audit

### Architecture as built

```
apps/web        Next.js App Router, styled-components, Supabase SSR   ← this audit
apps/mobile     Expo (React Native) — superseded, see below
packages/shared Towns, routes, shared types
supabase/       33 migrations, 10 Deno edge functions                 ← this audit
```

**Answering §8 of the MVP document directly.** It asks the team to *"audit the current TypeScript and Node backend first and refactor before we consider a rewrite"*, and states *"a managed PostgreSQL database is my preference for bookings and payments, subject to the audit."*

- **There is no Node backend to audit or refactor.** No Express, Nest or standalone API service exists, and none ever did in this repository. The assumption in §8 is out of date.
- **The managed PostgreSQL preference is already satisfied.** Supabase *is* managed Postgres, with point-in-time recovery and backups. Bookings and payments already live there. No migration is needed.

So "The backend" is three things:

1. **Next.js server actions** (`"use server"` in 8 modules) — the write path for trips, bookings, alerts, support, auth and KYC.
2. **Supabase PostgREST** — the read path, governed by RLS.
3. **Supabase edge functions** (Deno) — M-Pesa, escrow, refunds, wallet, email.

### Supabase is the backend for both clients

This is settled and it is the right call. Supabase already *is* the backend — Postgres, Auth, Storage, Realtime and edge functions — and the Kotlin app consumes the same project the web does. No second backend is being built. §1.1 sets out why that saves the most time and money of any decision in this plan.

The finding from this audit is narrower, and it is not an argument against the shared backend: **some business logic currently sits in Next.js server actions, which only the web can call.** Server actions are an internal Next transport, not HTTP endpoints. Every write — publishing a trip, reserving a seat, submitting KYC, opening a support case — lives there today.

So the work is not "build Kotlin an API". It is **finish moving the write path into Supabase**, where both clients already reach it. That is the same work the P0 payment and seat defects need (§5.1, §5.2, §5.4), so it should be costed once, not twice.

| Where logic lives today | Reachable by web | Reachable by Kotlin | Action |
|---|---|---|---|
| Postgres + RLS (reads) | Yes | Yes | Keep |
| Edge functions (money) | Yes | Yes | Fix identity handling (§5.1) |
| Postgres RPC (`deduct_seats`) | Yes | Yes | Start calling it (§5.2) |
| Next server actions (writes) | Yes | **No** | Move into edge functions or RPC |

**Scope of the move:** roughly 12 write actions that matter to a mobile client — trips, bookings, KYC, alerts, support. Auth actions stay where they are, because Kotlin uses the Supabase Auth SDK directly rather than our wrappers. Estimate **1–2 weeks**, overlapping almost entirely with the P0 fixes.

### 1.1 Why the shared Supabase backend is the right decision

Written out because the team and any new engineer should understand the reasoning, not just the instruction.

**It already exists and it already works.** 33 migrations, 41 tables, row-level security, authentication, file storage, realtime subscriptions and 10 deployed functions are live today. A separate backend starts at zero and has to re-earn all of it.

**Kotlin is a first-class client, not an afterthought.** `supabase-kt` covers Postgrest, Auth, Realtime, Storage and Functions, and targets Android, JVM and iOS. The Kotlin app gets the same primitives the web uses without anyone designing, documenting or versioning a bespoke API in between.

**One identity system.** Supabase Auth issues the JWT; both clients present it; Postgres reads it in RLS. Phone OTP, Google OAuth and magic links are already configured and working. A separate backend means a second session system and a token bridge between them — a classic source of security bugs.

**Authorization is written once, in SQL.** RLS policies are enforced by the database, so they apply no matter which client connects. With a separate backend, every rule is written twice and drifts. The Expo app proved this: it re-implemented booking rules client-side and they diverged.

**The API maintains itself.** PostgREST generates endpoints from the schema. Add a column, and both clients can read it the same day — no DTOs, no serializers, no endpoint to write, no version to deprecate.

**Realtime without running WebSocket infrastructure.** Booking, notification and message updates already stream over Supabase Realtime to any client. Building that separately means managing a socket layer, presence and reconnection.

**Storage with the same policy engine.** Avatars, vehicle photos, alert media and support attachments are already stored with RLS policies attached.

**Secrets stay server-side where they must.** Daraja keys, the escrow split and refund decisions live in edge functions. That is the correct boundary, and it is the same boundary a custom backend would need to build.

**The cost difference is ongoing, not one-off.** A separate backend adds: a service to host and scale, its own deployment pipeline, monitoring and on-call, a second set of secrets, a second thing to patch, and API documentation to keep honest. Supabase is one project, one bill, with backups and point-in-time recovery included. For a team of this size before revenue, that operational surface is the real cost — more than the build.

**It shortens the critical path.** The Kotlin app can start against a live, populated, authenticated backend on day one instead of waiting on an API contract. That matters directly to the 10 November start date in §9 of the MVP document.

**What this requires to stay true.** The advantages hold only while business rules live in Postgres (RLS, triggers, RPC) or edge functions. The moment a rule lives only in a client, the two clients diverge and the shared backend stops being shared. That is precisely what §5.2 and §5.4 show happening today — the seat rule is in a server action rather than in the database, and the driver rule is enforced nowhere. Fixing those is what makes the decision pay off.

### Observations

- **No tables exist for Kipita Send.** No parcels, shipments, capacity listings, handover codes or item declarations. Send is not behind a feature flag — it is unbuilt (§5.9).
- `conversations` and `messages` exist and are migrated, but **nothing on the web consumes them**. The chat schema is ready; the web client is not (§5.7).

## 5. Missing functionality and defects

Ordered by what blocks a paid pilot.

### 5.1 — P0 · Payment functions trust the client

`initiate-payment` reads `{ booking_id, user_id, amount, method, phone }` from the request body and runs on a service-role client (`supabase/functions/initiate-payment/index.ts:17-20`). **The amount charged is supplied by the caller.**

`release-escrow` checks ownership like this (`release-escrow/index.ts:63`):

```ts
if (driver_id && booking.driver_id !== driver_id) {
  return json({ error: 'Not authorized to release this payment' }, 403);
}
```

Omit `driver_id` from the body and the check does not run. Any caller who reaches the function with a `booking_id` releases that escrow and takes the fee.

`confirm-payment`, `check-payment` and `send-email` identify the subject from the body in the same way.

This contradicts MVP §6.6 — *"Payment status comes only from a verified server-to-server callback"* — and §7 — *"The backend is the source of truth for permissions, price, seats, capacity and payment status."*

**Fix:** derive identity from the JWT in all five, as `topup-wallet`, `withdraw-wallet`, `request-refund` and `resolve-refund` already do. Compute `amount` server-side from the booking. Add a signature or IP allowlist to `mpesa-callback`. **Do this as part of the write-path lift in §1, not separately.**

### 5.2 — P0 · Seats are never decremented; overbooking is possible

`reserveSeatAction` reads `seats_available` (`lib/bookings.ts:56-60`), checks it, then inserts a booking (`:100`). **It never decrements the seat count and never takes a row lock.**

`deduct_seats(p_ride_id, p_seats)` — which does `SELECT … FOR UPDATE` and decrements correctly — exists at `supabase/migrations/003_trip_model_restructure.sql:297` and **is never called from anywhere.**

Consequences today: a ride displays its original seat count forever regardless of bookings, and N passengers can each book the last seat. `UNIQUE(trip_id, passenger_id)` prevents one passenger double-booking; nothing else is enforced.

MVP P0 requires *"seat protection (no overbooking, holds that expire)"*. Neither half is implemented.

### 5.3 — P0 · No hold expiry

A booking is created at `pending_payment` and stays there indefinitely. There is no `expires_at` on `bookings` and no sweeper. An unpaid hold never releases its seat — which currently does not matter because of 5.2, but will the moment 5.2 is fixed.

### 5.4 — P0 · No server-side driver enforcement

The `trips` INSERT policy only checks `driver_id = me`. Nothing consults `driver_profiles`. **Any authenticated client can publish a trip** by calling PostgREST directly, bypassing `createTripAction`'s KYC gate.

`driver_profiles` RLS is `FOR ALL USING (own row)`, so a client can also write its own `approval_status`. The gate is in any case "has submitted", not "is approved" (`approval_status !== 'not_submitted'`).

**This is the rule that must move into the database, not stay in a server action.** The Kotlin client reaches Postgres through the same RLS the web does, so whatever RLS enforces is what both clients get. Today RLS enforces nothing about being a driver, and the only check lives in a function Kotlin cannot call. Put it in a policy or a trigger and both clients are covered at once — which is the shared backend working as intended (§1.1).

### 5.5 — Scope contradiction · Wallet and escrow are built

Decision 6: *"No wallet or escrow in the MVP — Decided."*

Already built and migrated: `wallets`, `wallet_transactions`, `wallet_topups`, `wallet_withdrawals` (migrations 013, 014, 025), `topup-wallet`, `withdraw-wallet`, `release-escrow`, a `/wallet` route, and an escrow hold/release model.

MVP §6.6 notes that holding or splitting customer money can bring Central Bank payment-service rules into play. **Live legal exposure, not a backlog item.** Either the decision changes, or these surfaces go behind a flag that stays off until counsel clears them.

In Kipita's favour: the platform fee is `KIPITA_FEE_PERCENT`, an environment variable defaulting to **12%** (`release-escrow/index.ts:9`). Under the 18% NTSA cap, and configurable, which is what §6.2 asks for.

### 5.6 — P0 (newly exposed) · Web push does not exist and is not trivial

Previously acceptable as mobile-only. With web as the only client, **booking updates cannot reach a user whose tab is closed.**

Today: the migration-007 notification trigger speaks the **Expo push API** only. Web has no service worker, no VAPID keys, and no subscription storage. Live-arrival notifications work only while a tab is open, over Realtime.

MVP §4 names push as a reason the real product is an app. If the web pilot is the paid pilot, this needs: a service worker, VAPID key pair, a `push_subscriptions` table, and the trigger rewritten to speak Web Push. **Estimate 3–5 days.** iOS Safari requires the user to install the PWA before it will deliver push at all — worth knowing before it is promised.

### 5.7 — P0 (newly exposed) · No chat on the web

`conversations` and `messages` are migrated and were used by the Expo app. **The web has no chat UI at all** — which is why "respond to this request" on web previously sent people to the app. There is no app to send them to now.

MVP P0 asks for "booking-linked chat". The schema is ready; the client is not. **Estimate 4–6 days** for a booking-scoped thread with Realtime and an unread count.

### 5.8 — Request-to-book is not implemented

MVP §7: *"Request-to-book first. Instant booking comes later."*

`reserveSeatAction` creates a pending booking immediately. There is no driver approval step, no request state, and no accept/decline surface. A scope gap rather than a bug — but a P0 one that changes the booking state machine, so it should be settled before the write path is lifted in §1.

### 5.9 — Kipita Send does not exist

No tables, no routes, no types, no feature flag. §7 lists Send as "P0 gated"; it is currently P-none. A design and legal spike before it is an engineering task.

### 5.10 — Other gaps

| Gap | Detail |
|---|---|
| Vehicle management | A vehicle row is created implicitly when a driver publishes with car details. There is no standalone vehicle CRUD or management screen. |
| Alert moderation | `announcements` has no UPDATE or DELETE policy. **No client, including admin, can remove an alert.** |
| Live alert feed | `announcements` is not in the `supabase_realtime` publication. |
| Daraja secrets | `MPESA_CONSUMER_KEY`, `MPESA_CONSUMER_SECRET`, `MPESA_SHORTCODE`, `MPESA_PASSKEY`, `MPESA_CALLBACK_URL`, `MPESA_BASE_URL` are **not set on the edge functions**. `initiate-payment` throws until they are. |
| Audit log | §8 of the MVP document requires one for every admin action. None exists. |
| Live trip tracking | Not built. Browsers do not deliver reliable background location, so on web this is a foreground-only feature. Scope it honestly or defer it to the Kotlin client. |

Proposed. Needs CEO sign-off to become the frozen scope under the 23 November gate.

### Recommended frozen scope

The mobile descope removes the fallback for items 9 and 10, and adds roughly **7–11 days** of work that was not in the plan. Two honest options:

**A — Full P0 (1–12).** Adds web push and web chat. Pushes the pilot start by about two weeks.
**B — Narrowed pilot (1–8, 11, 12), with 9 and 10 deferred.** The pilot runs with in-app notifications only while a tab is open, and WhatsApp as the out-of-band channel between driver and passenger — which is what Kenyan users do anyway, and the share-to-WhatsApp path already exists. Chat and push land before public launch.

**Recommendation: B.** It keeps the pilot date, tests the thing actually being proven (does a corridor fill?), and does not spend two weeks building a chat that a private pilot of 25 drivers may not need. It must be a conscious deferral with a date, not a silent gap.
